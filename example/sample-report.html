Executive summary

This review covers all 122 data models in the Northwind Trading Co. (sample) Sigma organization and a deep structural analysis of the 10 models on the governed surface. The portfolio is healthy in places — Revenue Gold DM shows the target pattern of reusable metrics (64) and declared relationships (27) — but three themes stand out. First and most important, 3 centralized models read from a sandbox/dev schema, a data-integrity risk worth fixing before anything else. Second, governance: 64% of models sit in personal spaces with only 1 promoted to production, and ~12 models are duplicates. Third, reusability: 5 of the analyzed models define no reusable metrics, and 5 rely on cross-element lookups that can break charts at view time. Each finding below includes the affected models and concrete next steps. This was a read-only review — no models were changed.

Detailed recommendations

1
CRITICAL Data integrityEffort: High · cross-team

3 governed data models read from a sandbox/dev schema (DEV_SANDBOX)

These models live on the centralized/production surface yet pull from a non-production schema. Anyone building on them is trusting numbers that can change or disappear without notice — this is a correctness and trust risk, not just housekeeping, which is why it ranks first.

Affected models
  • Legacy Orders DM 0. CENTRALIZED/Legacy
  • Inventory Snapshot DM 0. CENTRALIZED/Ops
  • Returns DM 0. CENTRALIZED/Ops
Recommended actions
  1. Confirm the production equivalent of each *_SANDBOX object with the data-engineering owner (most are DW_SALES / DW_ODS legacy lineage).
  2. Re-point each model's source element to the production schema; column references carry over unchanged when names match.
  3. Validate a known KPI on each re-pointed model against a trusted figure before publishing the new version.
  4. Add a lightweight standard: models under 0. CENTRALIZED… may only source from production schemas (a periodic re-run of this assessment enforces it).
2
HIGH CorrectnessEffort: Medium

5 models join across elements with Lookup() instead of declared relationships

A cross-element Lookup() is fine for a scalar measure, but the moment one is used as a grouping dimension in a chart, Sigma can only resolve a single external relation per query and the visual renders the literal error “Rollup cannot reference more than one external relation.” It surfaces at view time with no build-time warning, so it tends to be discovered by an end user.

Affected models
  • Sales Mart DM — 18 cross-element lookups, 0 declared relationships
  • Customer 360 DM — 12 cross-element lookups, 0 declared relationships
  • Inventory Snapshot DM — 2 cross-element lookups, 0 declared relationships
  • Marketing Spend DM — 2 cross-element lookups, 0 declared relationships
  • Pricing DM — 1 cross-element lookups, 0 declared relationships
Recommended actions
  1. For each model, identify the cross-element Lookup() columns and which are used as chart grouping dimensions downstream.
  2. Replace those with a declared relationship between the two elements so the query planner handles the join — or switch the element's source to a join so the dimension is baked into the SQL.
  3. Leave scalar-only lookups (numerator/denominator inside an aggregate) as-is.
  4. Start with Sales Mart DM (18) and Customer 360 DM (12) — the highest exposure.
3
MEDIUM GovernanceEffort: Medium · ongoing

4 duplicate clusters span ~12 data models (10% of the org)

Near-identical copies (e.g. X DM, X DM (1), X DM Test, UAT/backup variants) split usage and let definitions drift, so two dashboards on “the same” model can disagree.

Affected models
  • 4× Sales Mart DM 0. CENTRALIZED/Sales; My Documents
  • 3× Customer 360 DM 0. CENTRALIZED/CRM; My Documents
  • 3× Finance Targets DM FP&A/Models; My Documents/Archived Users/j.doe
  • 2× Returns DM 0. CENTRALIZED/Ops; My Documents
Recommended actions
  1. Pick the canonical version in each cluster (newest on the governed surface) and confirm it covers the others' columns.
  2. Re-point consumers to the canonical model, then archive the copies (archiving is reversible).
  3. Discourage “Save As” for shared models; promote a copy into a governed folder instead.
4
MEDIUM GovernanceEffort: Low policy · ongoing

78 of 122 models (64%) live in personal My Documents; only 1 sit in 1. PRODUCTION

Models in personal spaces aren't discoverable, owned, or promoted as a team asset, and they vanish when a person offboards (several copies already sit under Archived Users). The near-empty promotion path means “production” isn't yet the single source of truth.

Recommended actions
  1. Define a simple promotion path: personal → team/sandbox → 1. PRODUCTION, with an owner and a short review per promotion.
  2. Identify the handful of personal models that real dashboards depend on and promote them first.
  3. Re-run this assessment quarterly to watch the production count grow and sprawl shrink.
5
MEDIUM ReusabilityEffort: Medium

5 of 10 analyzed models define no reusable metrics

When a model has no metrics, every dashboard re-implements its own Sum()/CountDistinct() logic, so the same KPI drifts across reports and there's no governed definition to point to. Revenue Gold DM already does this well (64 reusable metrics) and is a good in-house template.

Affected models
  • Sales Mart DM — 190 calc columns, 0 metrics
  • Finance Targets DM — 70 calc columns, 0 metrics
  • Legacy Orders DM — 50 calc columns, 0 metrics
  • Inventory Snapshot DM — 30 calc columns, 0 metrics
  • Returns DM — 25 calc columns, 0 metrics
Recommended actions
  1. On each heavy model, promote the obvious aggregate calc columns (Sum([Net Revenue]) etc.) to element metrics with a clear name and description.
  2. Express ratios/derived KPIs once as metrics so consumers reference them instead of rebuilding.
  3. Lead with Sales Mart DM — the highest calc surface with zero metrics today.
6
LOW MaintainabilityEffort: Low per model

Large models repeat the same formula many times — e.g. Sales Mart DM has 3 repeated definitions

Identical formulas copied across elements mean a change has to be made in many places, and missing one creates a silent inconsistency. (Worst single model carries 190 calc columns.)

Affected models
  • DateTrunc("day", [As Of]) — defined 6×
  • [Gross Revenue] + [Adjustments] — defined 4×
  • DateAdd("day", -1, Today()) — defined 4×
Recommended actions
  1. Define each repeated expression once (a shared calc column or metric on the source element) and reference it everywhere else.
  2. Calendar/date helpers like DateTrunc("day", [As Of]) are good candidates for a single shared date element.
7
LOW DiscoverabilityEffort: Low

Many models leave imported elements unnamed

Consumers browsing the model see anonymous elements and can't tell one revenue slice from another without clicking in — friction that pushes them to rebuild rather than reuse.

Affected models
  • Revenue Gold DM — 48 unnamed elements
  • Legacy Orders DM — 14 unnamed elements
  • Customer 360 DM — 10 unnamed elements
  • Sales Mart DM — 9 unnamed elements
  • Returns DM — 6 unnamed elements
  • Finance Targets DM — 3 unnamed elements
Recommended actions
  1. Give every element a meaningful name (a ~30-minute pass per model).
  2. While there, fix typo columns that shadow the real one (e.g. Defintion vs Definition).
